    Part 1 · Module 10 — Modern Syntax & Tooling

    7253 Software Development Capstone · self-guided · work at your own pace

    🎯 Objective

    By the end of this module you can:

    • Reach into nested data safely with ?.
    • Supply a fallback with ??, and say how it differs from ||
    • Say what npm install actually did to your folder
    • Scaffold and run a Vite project
    • Have the shell of your P1 Data App running locally

    🔑 Why it matters

    This is the last module before the project. Two small pieces of syntax that will save you from a specific crash, and the tool every React project in the world is built with.

    By the end of this module you should have a Vite dev server running and your Data App's folder in existence. The build block opens next.

    IdeaWhere you meet it again
    ?.Reading API data, where a field you expected is sometimes just not there
    ??Defaults that survive 0 and "" — a real bug source
    npmEvery dependency you will ever add, and node_modules finally making sense
    VitePart 2. Every React project starts with the command you are about to run

    Optional chaining is not a style preference. It is what stops "Cannot read properties of undefined" — the single most common runtime error in JavaScript, and the one most likely to break your Data App in front of somebody.

    The one idea underneath all of it

    Real data has holes in it.

    Your own objects are always complete because you wrote them. Data from an API is missing fields, has nulls where you expected numbers, and changes shape between records. The two operators in this module exist entirely because of that, and everything about the Data App gets easier once you stop assuming the data is tidy.

    ⌨️ Build — data-app/

    Two parts today. First modern.js for the syntax, then a real Vite project that becomes your Data App.

    1 · ?. — reading data that has holes in it

    const user = { name: "Ada", address: { city: "London" } };
const other = { name: "Grace" };                 // no address at all

console.log(user.address.city);      // "London"
console.log(other.address.city);     // TypeError — the classic crash
    1. Run it and read the error properly: Cannot read properties of undefined (reading 'city')
    2. Fix it with other.address?.city and see undefined instead of a crash
    3. Chain deeper: other?.address?.city?.length
    4. Try it on a function that might not exist: obj.method?.()

    Done when: You can explain which thing was undefined in the original error — it was address, not city, and reading that correctly is half of debugging.

    This is the error you will hit most often for the rest of your life. Learn to read it: the thing in the parentheses is what you were trying to read; the thing that was undefined is what came before the dot.

    2 · ?? versus ||

    const score = 0;
console.log(score || 100);    // 100  — wrong! 0 is a real score
console.log(score ?? 100);    // 0    — right
    1. Run it and make sure the difference is genuinely clear
    2. Do the same with an empty string "" as a username
    3. Write down the rule: || triggers on falsy, ?? triggers only on null or undefined
    4. Combine them: const city = user?.address?.city ?? "Unknown";

    Done when: You can name two values where || gives the wrong answer. 0 and "" are the two that cause real bugs — a score of zero and a blank-but-valid name.

    Item 4 is the line you will write a hundred times in Part 2. Reach in safely, fall back sensibly. It is the whole pattern for rendering API data.

    3 · What npm actually does

    npm init -y
npm install dayjs
    1. Run both in a scratch folder and then look at what changed
    2. Open package.json and find dayjs in dependencies
    3. Look at node_modules/ — count the folders, and notice it is far more than one
    4. Find package-lock.json and read the first twenty lines
    5. Use it: import dayjs from "dayjs"; console.log(dayjs().format("YYYY-MM-DD"));

    Done when: You can say what each of the three artefacts is for: package.json is what you asked for, package-lock.json is exactly what you got, and node_modules is the actual code. And you know why node_modules is never committed.

    One install pulled in dozens of folders. Those are your dependency's dependencies. This is worth ten seconds of thought before you add a package for something you could write in five lines.

    4 · Your first Vite project

    npm create vite@latest data-app -- --template vanilla
cd data-app
npm install
npm run dev
    1. Run it and open the URL it prints
    2. Edit main.js, save, and watch the browser update without a refresh
    3. Read index.html and find the <script type="module"> line — that is Module 8's work showing up
    4. Stop the server, run npm run build, and look inside dist/

    Done when: The dev server hot-reloads, and you have looked inside dist/ and seen that your readable source has become something else entirely. That is the build step the Module 8 stretch was about.

    We use the vanilla template deliberately. No React yet — this is your Data App, and Part 2 starts a separate React project. Doing plain JS first means you will know which parts of Part 2 are React and which parts were always just JavaScript.

    5 · The shell of your Data App

    You have a Vite project. Make it the beginning of the real thing.

    1. Pick your API and write its URL in your log. It must return a list of something
    2. Move your Module 9 fetch function into data-app/src/api.js as a named export
    3. Import it in main.js, call it, and console.log the result
    4. Put one field from the first record onto the page with document.querySelector
    5. Confirm your error handling from M9 came along with it

    Done when: Real data from a real API is visible in a browser you are running. It is one field and it is ugly. It is also the project working end to end, which is the hardest part and it is now behind you.

    Choose an API that needs no key and allows browser requests. PokeAPI and JSONPlaceholder both work. If yours needs a key or blocks CORS, change it now rather than during the build block.

    Stretch · Look at what you shipped

    1. Run npm run build and note the file sizes Vite reports
    2. Open the built JS in dist/assets/ and try to read it
    3. Add dayjs to the project, use it once, rebuild, and compare sizes
    4. Write two sentences: what did one small dependency cost you?

    Done when: You have a number for what a dependency costs. That number is why "just npm install it" is a decision rather than a reflex.

    ✅ Check Yourself

    Can you, without looking anything up:

    • Say what ?. does when the thing before it is undefined?
    • Name two values where || gives the wrong default and ?? does not?
    • Explain the difference between package.json and package-lock.json?
    • Say why node_modules is not committed to git?
    • Say what npm run build produced and why a browser wants it?
    • Name your Data App's API and what it returns?

    If any box is unchecked, spend twenty minutes on that row's resource. Then check it.

    🏁 Done When

    • Real data from your chosen API is on the page — one field is enough
    • Your M9 error handling survived the move
    • Your log entry is written, including your API's URL and what it returns
